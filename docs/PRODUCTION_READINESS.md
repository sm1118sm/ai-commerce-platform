# StylePick AI 실제 운영 전환 가이드

## 1. 문서 목적

현재 StylePick AI는 로컬에서 회원가입부터 개인화 추천, 장바구니, 모의
주문까지 시연할 수 있는 캡스톤 MVP다. 이 문서는 현재 결과물을 인터넷에
공개하거나 실제 사용자가 이용하는 서비스로 전환하기 위해 앞으로 필요한
작업을 우선순위와 완료 조건까지 포함해 정리한다.

## 2. 현재 구현 상태

| 영역 | 현재 상태 | 운영 전환 시 필요한 작업 |
|---|---|---|
| 화면 | Streamlit 단일 웹앱 | 모바일 브라우저 점검, 접근성, 오류 화면 |
| 회원 | 이메일·비밀번호 회원가입과 로그인 | 이메일 인증, 비밀번호 재설정, 세션 만료 |
| 비밀번호 | PBKDF2 해시 | 비밀키 관리, 로그인 횟수 제한, 보안 감사 |
| 데이터베이스 | 로컬 SQLite | 관리형 PostgreSQL 이전, 마이그레이션·백업 |
| 상품 | 샘플 상품 30개 | 실제 상품·이미지·재고 관리 및 라이선스 확인 |
| 추천 | TF-IDF와 행동·트렌드 점수 | 실제 로그 평가, 가중치 실험, 품질 모니터링 |
| 행동 로그 | 조회·검색·찜·장바구니·구매 저장 | 수집 동의, 보관 기간, 익명화 정책 |
| 주문 | 모의 결제와 재고 차감 | 실제 결제 연동 또는 명확한 데모 표시 |
| 운영 도구 | 없음 | 상품·재고·주문·회원 관리 화면 |
| 배포 | 로컬 서버 | HTTPS 배포, 도메인, 상태 확인, 장애 대응 |

## 3. 운영 목표를 먼저 구분해야 하는 이유

### A. 캡스톤 공개 시연

교수와 평가자가 URL로 접속해 기능을 체험하는 것이 목표다. 실제 돈과
민감정보를 처리하지 않는다.

필요 조건:

- 로그인 또는 데모 계정
- 안정적인 클라우드 실행
- 외부 영구 데이터베이스
- 모의 결제임을 명확히 표시
- 개인정보 최소 수집
- 시연 데이터 초기화 방법

### B. 실제 소규모 운영

일반 사용자가 계정을 만들고 데이터를 장기간 사용하는 단계다.

추가 조건:

- 이메일 소유 확인과 비밀번호 재설정
- 개인정보 처리방침과 이용약관
- 관리자 기능
- 백업·복구·모니터링
- 보안 점검과 요청 제한
- 상품·재고 데이터 운영 절차

### C. 실제 판매 서비스

실제 결제, 환불, 배송, 고객 문의가 포함되는 상용 단계다. 현재 3일 캡스톤
범위 밖이며 결제·전자상거래·개인정보 관련 법률 검토가 필요하다.

## 4. P0 — 공개 시연 전에 반드시 해야 하는 작업

### 4.1 SQLite를 외부 PostgreSQL로 이전

SQLite 파일은 한 서버 내부에서만 안정적으로 사용할 수 있고, 무료 배포
환경에서는 재시작 시 파일이 사라질 수 있다. 여러 사용자가 동시에 쓰는
환경에도 적합하지 않다.

해야 할 일:

1. 관리형 PostgreSQL 인스턴스를 생성한다.
2. 현재 테이블을 PostgreSQL 문법으로 마이그레이션한다.
3. DB 접속 주소를 환경변수로 관리한다.
4. 연결 실패와 타임아웃을 사용자 오류 화면으로 처리한다.
5. 개발·테스트·운영 DB를 분리한다.
6. SQLite 데이터 이전 스크립트를 작성한다.

권장 환경변수:

```text
DATABASE_URL=postgresql://...
APP_ENV=production
SESSION_SECRET=충분히_긴_랜덤_문자열
DEMO_MODE=true
```

완료 조건:

- 앱 재배포 후에도 회원·찜·장바구니·주문이 유지된다.
- 두 명 이상이 동시에 사용해도 데이터가 섞이지 않는다.
- DB 장애 시 전체 스택 트레이스 대신 안내 문구가 표시된다.

### 4.2 인증 세션 강화

현재 로그인 상태는 Streamlit 세션 메모리에 존재한다. 공개 서비스에서는
브라우저 종료, 세션 탈취, 무차별 로그인 시도를 고려해야 한다.

해야 할 일:

- 이메일 인증
- 비밀번호 재설정
- 로그인 실패 횟수 제한
- 일정 시간 후 자동 로그아웃
- 비밀번호 변경
- 회원 탈퇴와 개인정보 익명화
- 비밀번호·DB 주소를 로그에 남기지 않기
- 운영 환경의 HTTPS 강제

완료 조건:

- 다른 브라우저에서 다른 회원의 데이터에 접근할 수 없다.
- 잘못된 로그인 반복 시 일시 제한된다.
- 탈퇴 회원은 다시 로그인할 수 없다.

### 4.3 비밀정보와 환경설정 분리

해야 할 일:

- `.env`, DB 파일, 비밀키를 Git에서 제외한다.
- 배포 플랫폼의 Secret 기능을 사용한다.
- 개발용 데모 계정 비밀번호를 운영 코드에 하드코딩하지 않는다.
- 운영 로그에 이메일 전체를 노출하지 않는다.

완료 조건:

```bash
git grep -n -E "password|secret|postgresql://" -- ':!docs'
```

검사 결과에 실제 비밀번호나 접속 주소가 없어야 한다.

### 4.4 실제 배포

캡스톤 공개 시연은 Streamlit 배포를 유지하는 것이 가장 빠르다. 단, 데이터는
외부 PostgreSQL에 저장해야 한다.

현재 프로젝트에는 `render.yaml`이 포함되어 있어 Render Blueprint로 웹
서비스와 PostgreSQL을 함께 생성할 수 있다. 무료 PostgreSQL은 시연에
적합하지만 30일 후 만료되고 자동 백업을 제공하지 않으므로 장기 운영에는
유료 DB 또는 별도 관리형 PostgreSQL이 필요하다.

필요 작업:

1. GitHub 저장소에 소스 코드를 올린다.
2. 배포 서비스에서 `app.py`를 실행 파일로 지정한다.
3. Python 버전을 3.11 또는 3.12로 고정한다.
4. 환경변수와 DB Secret을 등록한다.
5. HTTPS URL에서 가입·추천·주문 전체 흐름을 테스트한다.
6. 데모 전용 계정과 초기 데이터를 준비한다.

완료 조건:

- 새로운 브라우저에서 URL만으로 접속된다.
- 서버 재시작 후에도 데이터가 남는다.
- 모바일과 PC Chrome에서 핵심 흐름이 동작한다.

### 4.5 오류 처리와 로깅

현재 사용자 입력 오류는 일부 처리하지만 운영 로그 체계가 필요하다.

기록할 항목:

- 앱 시작·종료
- 회원가입·로그인 성공 및 실패
- 추천 생성 시간과 추천 개수
- DB 오류
- 주문 성공 및 실패
- 재고 부족

기록하면 안 되는 항목:

- 비밀번호
- 비밀번호 해시
- 전체 DB 접속 주소
- 불필요한 개인정보

완료 조건:

- 오류 발생 시 사용자는 이해 가능한 안내를 본다.
- 운영자는 로그에서 요청 시각과 실패 지점을 찾을 수 있다.

## 5. P1 — 실제 사용자 테스트 전에 필요한 작업

### 5.1 사용자 행동 수집 정책

행동 로그는 추천에 필요하지만 개인정보 관점에서 목적과 보관 기간을 정해야
한다.

결정할 내용:

- 어떤 이벤트를 수집하는가
- 추천에 어떤 가중치로 반영하는가
- 로그를 얼마나 오래 보관하는가
- 회원 탈퇴 시 어떤 데이터를 삭제·익명화하는가
- 사용자에게 개인화 추천 사용 여부를 선택하게 할 것인가

현재 이벤트:

| 이벤트 | 의미 | 추천 가중치 |
|---|---|---:|
| VIEW | 상품 상세 확인 | 1 |
| SEARCH | 검색 | 1 |
| WISHLIST_ADD | 강한 관심 | 4 |
| WISHLIST_REMOVE | 관심 감소 | -3 |
| CART_ADD | 구매 고려 | 5 |
| CART_REMOVE | 구매 의향 감소 | -2 |
| PURCHASE | 가장 강한 선호 | 8 |

추가하면 좋은 필드:

- 추천 영역에서 클릭했는지 여부
- 추천 노출 순위
- 추천 모델 버전
- 체류 시간
- 디바이스 유형

### 5.2 추천 모델 평가

현재 가중치는 설명 가능한 초기 정책이며 실제 사용자 정답으로 학습된 값은
아니다. 운영 전에는 추천이 인기순보다 나은지 검증해야 한다.

오프라인 평가:

- Precision@K
- Recall@K
- NDCG@K
- 카테고리 다양성
- 이미 본 상품 반복률
- 품절 상품 노출률

온라인 평가:

- 추천 클릭률
- 추천 상품 찜 전환율
- 장바구니 전환율
- 모의 주문 전환율
- 추천 없음 또는 인기순 대비 A/B 테스트

평가 데이터 분리:

```text
과거 행동 → 학습·프로필 생성
가장 최근 행동 → 정답
```

완료 조건:

- 인기순 베이스라인과 같은 사용자 집단에서 비교한다.
- 추천 모델 버전과 가중치를 결과와 함께 기록한다.
- 특정 회원이나 카테고리에만 성능이 치우치지 않았는지 확인한다.

### 5.3 상품 관리

실제 운영에서는 CSV를 직접 수정하는 방식이 부족하다.

필요한 기능:

- 상품 추가·수정·비활성화
- 가격·재고 변경
- 품절 표시
- 상품 이미지 업로드
- 카테고리와 태그 관리
- 재고 변경 이력
- 주문 시점 가격 스냅샷

상품 이미지 사용 전 저작권과 상업적 사용 조건을 확인해야 한다.

### 5.4 최소 관리자 화면

관리자 권한에서만 접근할 수 있어야 한다.

필수 기능:

- 회원 목록과 상태 조회
- 상품·재고 관리
- 주문과 주문 상품 조회
- 행동 로그 집계
- 추천 클릭·주문 전환 현황
- 데모 데이터 초기화

관리자 비밀번호와 초기 계정을 코드에 직접 작성하면 안 된다.

### 5.5 주문 안정성

현재 모의 주문에도 서버 가격 재계산, 재고 확인, 트랜잭션이 적용돼 있다.
실제 운영 전에는 다음을 추가한다.

- 중복 주문 방지용 idempotency key
- 주문 상태 변경 이력
- 취소 시 재고 복구
- 주문 실패 시 트랜잭션 롤백 테스트
- 금액·수량 상한 검증
- 동시에 마지막 재고를 주문하는 경쟁 조건 테스트

## 6. P2 — 실제 판매 서비스로 발전할 때 필요한 작업

### 6.1 실제 결제

결제창을 직접 만들거나 카드 정보를 저장하지 않는다. 검증된 결제대행사의
테스트 결제부터 연동한다.

필수 흐름:

```text
주문 임시 생성
→ 결제대행사 결제 요청
→ 서버에서 결제 승인 검증
→ 주문 결제완료 처리
→ 실패 시 주문 취소
```

필요 사항:

- 결제 금액 서버 검증
- Webhook 서명 검증
- 중복 승인 방지
- 취소·환불
- 거래 기록과 주문 기록 대조
- 테스트 키와 운영 키 분리

### 6.2 배송과 고객지원

- 배송지 암호화 저장
- 배송 상태
- 취소·교환·환불
- 고객 문의
- 주문 알림

### 6.3 프론트엔드와 백엔드 분리

사용자 수와 화면 복잡도가 커지면 다음 구조로 전환한다.

```text
React 또는 Next.js
        ↓ HTTPS API
FastAPI
  ├── 인증 서비스
  ├── 상품 서비스
  ├── 추천 서비스
  └── 주문 서비스
        ↓
PostgreSQL
```

초기에는 마이크로서비스로 나누지 않고 하나의 FastAPI 애플리케이션을
사용한다. Redis, 메시지 큐, 별도 AI 서버는 실제 병목이 확인된 후 도입한다.

## 7. 데이터베이스 운영 설계

운영에 필요한 주요 테이블:

```text
users
user_preferences
products
user_favorites
user_cart
behavior_logs
recommendation_impressions
user_orders
order_items
inventory_history
model_versions
```

추가 원칙:

- 모든 외래키를 활성화한다.
- 이메일에는 UNIQUE 제약을 둔다.
- 가격과 수량은 음수가 될 수 없게 한다.
- 행동 로그의 사용자·시각·상품 인덱스를 유지한다.
- 주문 상품에는 주문 당시 이름과 가격을 저장한다.
- 스키마 변경은 버전이 있는 마이그레이션으로 관리한다.

백업 정책 예시:

- 매일 자동 백업
- 최소 7일 보관
- 월 1회 복원 테스트
- 배포 전 수동 백업

## 8. 테스트 계획

### 단위 테스트

- 비밀번호 해시와 검증
- 이메일·수량·가격 검증
- 추천 점수 범위
- 최근성 가중치
- 추천 이유와 실제 점수 일치

### 통합 테스트

- 회원가입 → 로그인 → 취향 저장
- 상세 클릭 → 로그 저장 → 추천 변화
- 찜 → 추천에서 기존 찜 제외
- 장바구니 → 주문 → 재고 차감
- 주문 실패 → 재고와 장바구니 유지
- 회원 A와 B의 데이터 분리

### 보안 테스트

- SQL Injection 입력
- HTML·스크립트 입력

## 15. 운영 준비 완료의 정의

다음 조건을 모두 만족하면 “캡스톤 데모”가 아니라 “공개 사용자 테스트가
가능한 앱”으로 판단한다.

1. 외부 HTTPS URL에서 접속할 수 있다.
2. 재배포 후에도 사용자 데이터가 유지된다.
3. 회원별 데이터가 섞이지 않는다.
4. 비밀번호와 DB 비밀정보가 노출되지 않는다.
5. 전체 구매 흐름이 3회 연속 성공한다.
6. 장애 발생 시 로그에서 원인을 찾을 수 있다.
7. DB 백업을 실제로 복원해본 기록이 있다.
8. 개인정보와 행동 로그 수집 목적을 사용자에게 안내한다.
9. 추천 결과를 인기순 기준과 비교할 수 있다.
10. 테스트·배포·복구 절차가 README에 기록되어 있다.
